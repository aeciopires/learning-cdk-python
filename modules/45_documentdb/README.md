# Module 45 - DocumentDB

## Overview

Amazon DocumentDB (with MongoDB compatibility) is a managed document
database: you store JSON-like documents, and applications talk to it with
a regular MongoDB driver and connection string. This module creates one
DocumentDB cluster with a single `db.t3.medium` instance, in its own
dedicated 2-AZ VPC, reachable only from inside that VPC on port 27017, with
storage encryption on and a master password generated by AWS Secrets
Manager.

It's module 45 (added after the original 44), but it belongs with the
other databases - see Phase 5 in
[`../../docs/LEARNING-PATH.md`](../../docs/LEARNING-PATH.md).

**Read [Notes and cautions](#notes-and-cautions) before deploying this
module to a real AWS account.** Like RDS/Aurora, a DocumentDB instance
bills hourly the moment it exists.

## What you will learn

- **Cluster vs. instance.** Like Aurora (module 20), DocumentDB separates
  the *cluster* (the replicated storage and the endpoints) from its
  *instances* (the compute that serves queries). `DatabaseCluster` creates
  both: here one `AWS::DocDB::DBCluster` and one `AWS::DocDB::DBInstance`.
- **An L2 construct for a database.** `aws_cdk.aws_docdb.DatabaseCluster` is
  a curated L2 construct - it creates the subnet group and wires the
  instances to the cluster for you, unlike the L1-only ElastiCache (22) and
  MSK (46) modules.
- **Generating a password without ever seeing it.** A Secrets Manager secret
  generates the password, and the cluster receives it as a
  `{{resolve:secretsmanager:...}}` *dynamic reference* - CloudFormation
  reads the secret at deploy time, so the password is never in the code or
  the synthesized template.
- Why the VPC spans two Availability Zones (`max_azs=2`): the construct's
  own documentation says its subnets must be "at least 2 subnets in two
  different AZs" - the same rule RDS has (module 18).

## AWS services and CDK constructs used

| AWS service | CDK construct (Python) | Level |

## Tests

New to this repository's tests? Read
[`../../docs/TESTING.md`](../../docs/TESTING.md) first - it explains, from
zero, what a CDK unit test is and how to write your own.

This module's tests
([`../../tests/unit/test_45_documentdb.py`](../../tests/unit/test_45_documentdb.py))
check that: exactly one `AWS::DocDB::DBCluster` and one
`AWS::DocDB::DBInstance` are created; the cluster is named by the naming
policy, runs engine version `8.0.0` on port 27017, and has storage
encryption on; the instance is a `db.t3.medium`; the subnet group spans two
subnets; the master password comes from a generated Secrets Manager secret
and reaches the cluster only as a `{{resolve:secretsmanager:...}}` dynamic
reference; the cluster is deleted with the stack; and every mandatory tag
(see [`../../REQUIREMENTS.md`](../../REQUIREMENTS.md) section 7) is present.
They run in under a second, with no Docker, no floci, and no AWS
credentials:

```bash
# From the repository root:
uv run pytest tests/unit/test_45_documentdb.py -v
```

## Deploy with floci (local, free)

```bash
# From the repository root - see ../../REQUIREMENTS.md for eval $(floci env)
eval $(floci env)
uv run cdk bootstrap   # once per floci instance - safe to re-run; see REQUIREMENTS.md section 5.7
uv run cdk synth DocumentDbStack
uv run cdk diff DocumentDbStack   # what deploy would change - creates nothing (REQUIREMENTS.md section 5.11)
uv run cdk deploy DocumentDbStack --require-approval never --method=direct
```

**What floci creates here (checked while writing this module - re-check
with newer floci versions):** the deploy succeeds and the VPC, security
group, and Secrets Manager secret are created, but floci's CloudFormation
implementation records the DocumentDB cluster and instance without
creating them - `aws docdb describe-db-clusters` returns an empty list
afterwards. floci's DocumentDB *API* does create clusters, so you can try
the service itself by calling it directly (see [Verify](#verify)).

## Deploy to real AWS (optional)

Only do this if you have read and understood
[Notes and cautions](#notes-and-cautions) - this module has a real,
ongoing hourly cost the moment it is deployed.

```bash
unset AWS_ENDPOINT_URL   # stop pointing the AWS CLI/SDK at floci
uv run cdk bootstrap --profile <your-aws-cli-profile>   # once per AWS account/region
uv run cdk diff DocumentDbStack --profile <your-aws-cli-profile>   # review the changes first
uv run cdk deploy DocumentDbStack --profile <your-aws-cli-profile>
```

## Verify

On real AWS:

```bash
aws docdb describe-db-clusters --query "DBClusters[].{Id:DBClusterIdentifier,Status:Status,Engine:EngineVersion,Encrypted:StorageEncrypted}"
aws docdb describe-db-instances --query "DBInstances[].{Id:DBInstanceIdentifier,Class:DBInstanceClass,Status:DBInstanceStatus}"
# the generated credentials (keep the output private):
aws secretsmanager get-secret-value --secret-id learning-cdk-python-dev-secret-docdb --query SecretString --output text
```

On floci, check the secret and what CloudFormation recorded, then
(optionally) create a cluster through floci's DocumentDB API to try the
service itself - and delete it afterwards:

```bash
aws secretsmanager describe-secret --secret-id learning-cdk-python-dev-secret-docdb --query Name
aws cloudformation describe-stack-resources --stack-name DocumentDbStack \
  --query "StackResources[].[ResourceType,ResourceStatus]" --output table

aws docdb create-db-cluster --db-cluster-identifier try-docdb --engine docdb \
  --master-username tryuser --master-user-password 'try-Passw0rd'
aws docdb describe-db-clusters --query "DBClusters[].[DBClusterIdentifier,Status]"
aws docdb delete-db-cluster --db-cluster-identifier try-docdb --skip-final-snapshot
```

(A password typed on the command line, as above, is fine for a throwaway
local cluster - never for a real one.)

Or open the floci UI at `http://localhost:4566/_floci/ui` and browse the
resources visually.

## Notes and cautions

- **Bills hourly on real AWS**, like RDS/Aurora: the `db.t3.medium`
  instance is billed continuously from creation until `cdk destroy`, plus
  storage and I/O. `db.t3.medium` is the smallest instance class
  DocumentDB offers. Check current rates for your region before deploying.
- **Engine version `8.0.0` and `db.t3.medium`**: the DocumentDB "Managing
  instance classes" page lists `db.t3.medium` as supporting engine
  versions 3.6.0, 4.0.0, 5.0.0, and 8.0.0 (checked while writing this
  module). Not every class supports every version, and versions reach end
  of support - re-check that page before changing either value.
- **Why the secret is created explicitly.** The shorter form,
  `docdb.Login(username="docdbadmin")` with no password, makes
  `DatabaseCluster` generate its own secret *and* add an
  `AWS::SecretsManager::SecretTargetAttachment`, which also writes the
  cluster's host and port into the secret. That attachment fails to deploy
  on floci ("DocDB cluster ... not found", because floci doesn't create
  the cluster itself - see [Deploy with floci](#deploy-with-floci-local-free)).
  Creating the secret explicitly keeps the module deployable on floci; the
  trade-off is that the secret holds only the username and password, and
  `cluster.secret` is `None` (so CDK's built-in rotation helpers aren't
  available). On a real-AWS-only project, the shorter form is the usual
  choice.
- **Deleted with the stack, with no final snapshot**
  (`RemovalPolicy.DESTROY`, `deletion_protection=False`) - a learning-path
  choice so `cdk destroy` leaves nothing behind. A production cluster
  should keep deletion protection on and a snapshot-on-delete policy.
- **Single instance, no replicas**: a production cluster usually adds at
  least one replica instance in another AZ for failover.
- **TLS:** "By default, encryption in transit is enabled for newly created
  Amazon DocumentDB clusters", so clients must connect with TLS - see
  [Encrypting data in transit](https://docs.aws.amazon.com/documentdb/latest/developerguide/security.encryption.ssl.html)
  and the DocumentDB guide's "Connecting programmatically" page for what a
  MongoDB client needs.
